# HANDOFF 写作指南(创建或修改 HANDOFF.md 前必须整篇读完)

质量基准:一个零上下文的新 agent,只凭这份文件 + 它指向的资源,能在一小时内恢复对项目的
完全控制。达不到这个基准的 HANDOFF 是装饰品。

## 定位与反定位

只回答一个问题:**如何从一无所有到完全接管**。它不是 dev-log(过程去 dev-log/)、不是任务清单
(去 TASKS.md)、不是 README(项目介绍去 README)、不是技术文档(机制去 wiki)、不是状态快照
(实况用验证命令现查)。发现自己在写"我们完成了/当前版本是"→ 立刻停下,放错地方了。

## 五段写法与质量标准

### 1. 这是什么
一两句定性(这是控制平面还是业务仓库?管什么?)+ **受控对象清单表**。多仓库/多实例项目必须建表,
每行:对象名 | 仓库(owner/repo) | 分支 | 运行目录/机器 | 线上入口 | 服务单元(systemd/worker 名)。
注意快照红线:分支、目录、入口、服务名是**结构**(可写);HEAD、commit、版本号、Worker version 是
**快照**(禁写,改为给查询命令)。

### 2. 资产与访问
- **机器表**:每台机器 IP/域名 | 用户 | 密钥文件路径(相对仓库) | 用途与职责边界(在这台机器上
  允许干什么、禁止干什么)。有"哪台机器负责哪类工作"的分工规则时必须写成禁令句
  (如"业务编译部署只在 65;本机只放总控,禁止业务开发")。
- **克隆后第一条命令**(权限修复类)置顶加粗。
- **凭据**:只写名字/位置/用途/获取方法,指向 secrets 索引文件;值一个都不许出现。
  写明恢复路径(vault URL 与 pull 方法,口令向用户索要)。
- **历史暴露标记**:凭据曾在聊天/日志中暴露过的,标注"待轮换",并写轮换后要更新哪里。

### 3. 接手阅读顺序
编号列表,**每项后面写一句"读它拿到什么"**(如".brain/wiki/index.md——踩坑与机制,接手前必读")。
顺序原则:规则类(AGENTS/CONVENTIONS)→ 本文件 → wiki index → 任务与状态 → 清单与凭据索引 →
按需的 runbooks。引用另一个仓库时必须给出本机路径与 GitHub 地址两个坐标。
被引用文档已知失效/腐烂的,**必须在此显式警告并写明以何为准**,不许一句"注意校准"带过。

### 4. 如何验证已接管成功
- 分两级:**必过项**(失败即未接管)与**实况绘图项**(探测世界现状,死活都是有效答案)。
- 每条命令带**预期输出**(→ active / → 401 / → repo-ok),接手者不用猜什么算过。
- 每条写入前问自己:"换一个 commit、换一台接手机器,它还成立吗?"不成立的不是验证命令,是快照。
- 全部命令必须在写入当下真实跑过;有副作用的命令注明(POST/写库类给替代的只读探测)。
- 正式交接场景:在此指向 `.brain/HANDOFF_ACCEPTANCE.md` 契约与报告要求(见 acceptance 指南)。

### 5. 雷区
每条是**禁令句 + 后果**("禁止 reset 生产脏工作树——/opt/auto-parse 长期带生产脏文件,重置即事故")。
必含:不可逆操作禁令、已知脏状态、架构不变量(画出调用链 + "X 不得直接调 Y")、
环境陷阱(代理/权限/工具怪癖)。来源:wiki 词条里的坑逐条检查是否够格上升为雷区。

## 收尾自检(逐项过,过不了不许提交)

1. 零上下文测试:遮住会话,只读本文件,能否说出"第一条命令敲什么"?
2. 全部验证命令本次实跑过,预期输出与实测一致?
3. 全文 grep 无密钥值、token、密码?
4. 无快照(commit/版本号/易变 URL)混进稳定段落?
5. 每个 TODO 都是"问谁、问什么、答案落哪"的可执行问句?
6. 引用的每个文件/路径都存在(或标注了 TODO)?
7. 更新触发器仍然只有世界结构变化(本次改动若只是任务进度,就不该动本文件)?
