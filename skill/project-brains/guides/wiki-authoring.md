# wiki 写作 schema(创建或修改词条前必须整篇读完)

本库是 **llm-wiki**:可复利、可游走、可审计的知识图谱,不是文章合集。
衡量线:**从任意节点出发,沿带类型的关系至少游走 3 步不断链。**
项目名只是 `source` 标签,**不是分类维度**——节点是知识本体(概念/实体),不是"某项目的一篇文章"。

## 准入红线(先过这一关,过不了根本不该进 wiki)

wiki 只收**无状态、跨项目通用、对某个问题的专业解答**。判据一句话:
**「换一个毫不相干的项目,这条还有用吗?」有 → wiki;只对本项目有用 → 不是 wiki。**

**明确不属于 wiki**(放错=污染中央库,应进 `.brain/conventions/`):
- 本项目的设计语言 / 代码规范 / UI 约定 / 词汇表(如"某产品的 11 条页面规则");
- 会演进、带"尚未实施/待办"的活文档(有状态);
- 只在本项目代码库里成立的踩坑(通用原理可抽成 wiki,项目实例留 conventions)。
这类是项目规矩,归 `conventions/`,**永不同步中央库**。wiki 里的每个节点都要能脱离本项目独立成立。

## 一、五类节点(type,必选其一)

| type | 是什么 | 命名 | 例 |
|---|---|---|---|
| **concept** | 机制/方法/定律,跨项目可复用的抽象知识 | 语义名 | `软硬纪律定律`、`SPA缓存头分工` |
| **entity** | 具体工具/服务/系统/协议 | 专名 | `codex-hooks`、`Cloudflare-Global-Key`、`Playwright` |
| **pitfall** | 一次具体的坑 + 判定指纹(可复现) | 症状名 | `cfk_用Bearer报1010`、`headless进程泄漏` |
| **comparison** | 2+ 实体/方案的对比 | `A-vs-B` | `提示词-vs-skill-vs-hook` |
| **overview** | 同主题 ≥2 节点时的综合(L2) | 主题名 | `agent纪律设计`、`CF认证陷阱全景` |

**禁止提炼行业公知**:RAG、Docker、Git、负载均衡、"最佳实践"这类在库外能搜到完整定义、
本库无增量的概念,即使被提及也不建节点。只提炼有独特视角、具体实现、或本库新命名的知识。

## 二、关系带类型(不写裸 [[link]])

正文用 `[[目标]]`,并在关系区显式声明类型:
```
## 关系
- 实现 [[软硬纪律定律]]         (本节点是该定律的一个实现)
- 对比 [[API-Token]]            (与之相对的另一方案)
- 依赖 [[Chromium]]
- 实例证明 [[Cloudflare-Global-Key]]  (pitfall→它印证的 concept/entity)
- 推翻 [[旧结论slug]]
```
关系类型闭集:`实现 / 对比 / 依赖 / 竞争 / 实例证明 / 属于 / 推翻 / 关联`。
**每个节点 ≥2 条出链,且目标必须存在**(死链禁止入库)。

## 三、三层置信(frontmatter `layer`)

- **L1 事实**:实测、源码、官方文档直接支持。断言要能回溯到证据(证据流/命令输出/源码路径)。**禁止把推测写成事实。**
- **L2 推断**:≥2 个 L1 的跨项目归纳(如"三个项目都栽在 CF 认证 → 通病")。必填 `confidence: high|medium|low` + `reasoning: 一句话依据`。
- **L3 问题**:悬而未决的假设/证据缺口,指导后续,不作既定事实。

## 四、frontmatter(6 必填,ingest 机读校验,缺一退回)

```yaml
---
title: 节点标题
type: concept|entity|pitfall|comparison|overview
tags: [标签]
summary: 一句话核心(检索用)
source: [项目名]        # 哪个/哪些项目产生,可多值
layer: L1|L2|L3
confidence: high|medium|low   # L2/L3 必填
reasoning: 推理依据            # L2/L3 必填
---
```

## 五、正文结构与质量硬闸

**concept/entity 页**(正文 ≥200 字,ingest 拦截字数):
- **定义/定位**:精确 ≤3 句,含关键技术细节,不空洞;
- **本库中的具体例子**:必须引用具体项目/命令/源码路径/数据(✅"在 codex 0.146 中 hooks 走 config.toml 数组表" ❌"多处均有体现");
- **机制/实现细节**:1-2 个关键点;
- **与近邻的边界**:区分容易混淆的相邻知识;
- **关系**:≥2 条带类型出链。

**pitfall 页**:症状 → **判定指纹**(怎么一眼认出是它,可复现命令)→ 根因 → 处置 → `实例证明` 它印证的 concept/entity。

**comparison 页**:对比维度表(维度|A|B)→ 核心差异 → 适用场景结论 → 双向链到被比较节点。

**overview 页**:主题边界 → 跨节点综合发现(L2,附 reasoning)→ 开放问题(L3)→ 引用所有相关节点。

## 六、触发规则(自动生长图谱)

- 一次踩坑 → pitfall 页,并 `实例证明` 链到它暴露的 concept/entity(没有就同时建 concept);
- 两个方案被对比 → 必建 comparison 页;
- 同主题 concept/pitfall ≥2 → 必建或更新 overview 页(这是跨项目复利的来源);
- 深度研究 → concept 页可写千字级(五段是下限),但仍按本 schema 分节点,不写成一篇大杂烩。

## 七、反模式(出现即返工)

1. **按项目组织**:把节点当"某项目的文章"。项目是 source 标签,节点是知识本体。
2. **裸链**:`[[x]]` 不声明关系类型。
3. **资产泄漏**:IP/端口/凭据路径入正文(外引 HANDOFF,见 [[wiki-vs-handoff-boundary]])。
4. **转录**:粘贴对话/命令记录原文。
5. **空洞**:concept 无具体例子、entity 无实现细节、pitfall 无判定指纹。
6. **孤儿/死链**:无出入链、或链到不存在的节点。
7. **公知**:提炼行业常识型概念。
8. **推测冒充事实**:L2/L3 内容标成 L1。

## 八、index 与 log

index.md 按 type 分区(## concepts / ## entities / ## pitfalls / ## comparisons / ## overviews),
每条 `- [slug](slug.md) — summary`。入库同时 log.md 追加 `## [日期] ingest type | slug`。
