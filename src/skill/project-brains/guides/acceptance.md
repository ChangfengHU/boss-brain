# 交接验收契约指南(正式交接/接管声明前必须整篇读完)

核心纪律:**"已了解"不是验收,声明"交接成功/接管成功"是有硬前提的**——
全部必选项 PASS + 验收报告已提交(push 需用户同意)。缺一样,只能说"部分接管,阻塞如下"。

## 契约文件 `.brain/HANDOFF_ACCEPTANCE.md`

正式交接的项目应有此文件(没有时,由 /handoff 提议生成)。结构:

```markdown
# 交接验收契约 — <项目名>
## 必选项(任一 FAIL/BLOCKED 即不得声明交接成功)
| # | 验收项 | 验证命令/方法 | 判定标准 |
## 可选项(记录实况,不阻塞声明)
```

验收项的来源:HANDOFF 验证段全量收录 + 逐个资产问"控制它需要证明什么"——
机器(SSH 通)、每个仓库(读**写**都要证明,git push --dry-run 或权限 API)、每个线上服务
(健康+鉴权两条)、每条业务链路(真实调用一次,不是 curl 首页)、密钥文件(存在+权限位)、
构建/CI(真实产出一次工件,如预览二维码/生成一张图)。

## 执行纪律

- 逐项执行,每项只允许四种结论:**PASS / FAIL / BLOCKED / NOT_RUN**。
- FAIL 必须附:失败命令、脱敏错误输出、初步归因。
- BLOCKED 必须附:阻塞原因、需要谁做什么才能解除(如"需用户提供新鲜分享链接")。
- NOT_RUN 必须附:为什么没跑(如"有副作用且非必选")。
- 禁止把"命令能跑"当"业务能用":解析服务要真解析一条链接,生图要真出一张图并拿到公网 URL。

## 验收报告

写入 `.brain/handoff-reports/<UTC时间>-<事件>.md`(如 `20260806T0300Z-takeover.md`):
结论首行(交接成功 / 未成功+阻塞数)→ 逐项结果表 → FAIL/BLOCKED 详情 → 遗留风险与下一步。
报告 commit(本地);**push 前征得用户同意**;未 push 时结论必须写"仅本地,远端未同步"。

## 与命令的关系

- `/takeover`:项目有契约文件 → 按契约逐项执行并出报告;没有 → 按 HANDOFF 验证段执行,
  并提议补建契约文件。
- `/handoff`:交接就绪检查的最后一步是核对契约文件本身是否过期(资产变了验收项没跟上)。
