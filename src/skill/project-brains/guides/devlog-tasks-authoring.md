# dev-log 与 TASKS 写作指南(写这两类文件前必须读完)

## dev-log(`.brain/dev-log/<YYYY-MM-DD>.md`)

单元 = 当天文件里的一节 `## <主题>`(一个会话/一个主题一节,同天多节追加)。

每节必答四问(有则写,无则省,但"卡在哪"永远不许隐瞒):
1. **做了什么**:结果导向的一两句,不是 git log 复读;
2. **为什么**:动机与约束(用户要什么、被什么逼的)——这是 dev-log 独有价值,commit message 装不下;
3. **卡在哪**:走过的弯路、当前未解决的问题、诡异现象(哪怕最后绕过去了也要记,它是未来的 wiki 原料);
4. **下一步**(会话没做完时):具体到"第一条命令"级别,给续接者/明天的自己。

与 evidence 的分工:evidence 是机器可读的账本(引用 task id、verify、exit),dev-log 是给人和
未来 agent 读的叙事;同一时刻写,内容互补不互抄。补账写的节,标题后缀 `(补账)`,绝不冒充当场记录。

反模式:流水账("改了 A 又改了 B")、无动机、报喜藏坑、写成周报腔。

## TASKS(`.brain/TASKS.md`)

- 行格式:`t-<序号> <一句可验收的描述> <active|blocked|done>`。id 一旦分配永不复用。
- **描述必须可验收**:写"目标态"不写"动作"("小程序 0.9.32 真机验收通过" 而非 "继续搞小程序")。
- blocked 必须在行内注明卡在谁/什么(`blocked: 等用户提供新鲜分享链接`)。
- **防腐**:收工清单扫一遍 active/blocked 项——状态变了当场改;连续两周没动的 active 项要么
  降级 blocked(写明卡点)要么关闭,不许"看板上永远 In Progress"(外部审计抓过 2 个月的僵尸任务)。
- 立新任务的时机:会话内容不属于任何现有任务时。并发第二任务出现时才分裂 `tasks/<id>/` 目录。
- 完成的任务行保留(done),它是 dev-log 的目录索引;别删除历史。
- **考古/补账建的任务**:验收标准写不实就写推断的目标态,并标注"状态为推断,待用户校准"——推断不标注等于冒充事实。
